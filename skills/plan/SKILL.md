# Develop a CT test plan

Turn a scope of work into a plan CheckThat can run. Ask before you assume. Read the format files; do not copy their rules into the plan from memory.

## 0. Locate the tools

The tools root holds `tools/ct.py`, `schema/test-plan.schema.json`, `docs/test-plan.md`, `openspec/specs/test-plan-format/spec.md` and `CheckThat/Model/Plan.lua`. A path counts as the root only when all five exist under it.

1. Try `ct/` beside this file. `make install-skill` puts it there with a private Python at `.venv/` beside this file. Call the root `$CT`. Set `$PY` to `.venv/bin/python` beside this file when it exists (`make install-skill`). A plugin or toolkit install has none: use the per-user Python that `ct setup` creates when it exists: `$XDG_DATA_HOME/checkthat/venv/bin/python` (default `~/.local/share/checkthat/venv/bin/python`; on Windows `%LOCALAPPDATA%\checkthat\venv\Scripts\python.exe`), else `python3` when `python3 -c "import yaml, jsonschema"` succeeds. If neither works, stop, tell the author to run `python3 $CT/tools/ct.py setup` once (it creates the per-user Python, which survives a plugin update), and do not claim a plan was validated. `$PY $CT/tools/ct.py doctor` shows which Python and LuaJIT the tools find. `$CT/tools/ct` is a launcher that picks the right Python, so a consumer can write `ct validate plans/x.yaml`; `make install-skill BIN_DIR=<folder on PATH>` puts a copy on the path. Read `$CT/VERSION` and tell the author which tools version you use. Only an installed bundle has that file; in a checkout say that you use the checkout. When the bundle has `VERSION` and the author's CheckThat checkout is known, compare it with `## Version:` in the checkout's `CheckThat/CheckThat_Vanilla.toc`. If they differ, warn that the bundle is stale and name the update for the install: `claude plugin update checkthat@checkthat` for the plugin, the newer zip from the GitHub release for a toolkit install, else `make install-skill`.
2. Else try two folders up from this file (the skill runs inside the checkout). Call that root `$CT`; use `$CT/.venv/bin/python` as `$PY` if it exists, else `python3` under the same import check and stop rule as step 1.
3. If neither is a root, ask: "Where is your CheckThat checkout?" Say that `make install-skill` in it sets up the skill for use anywhere. Do not draft until you have a root. Do not use the working directory; it may belong to another addon.
4. Read `$CT/docs/test-plan.md`, the format spec and the schema. Read `reference.md` and `example.yaml` beside this file. Read `$CT/docs/debug-logging.md` before the evidence question; if it is missing, say so and go on.

## 1. Interview

Ask **one question per turn** and wait for the answer. For each question say why it matters and which decision it unlocks, and offer a recommended answer where the repository supports one. Ask in this order. Skip a question when the OpenSpec change, specs or code already answer it, and say what you assumed. Code may settle facts (the addon, its slash prefix, which lines it logs). It never settles the author's choices (depth, locale, clients, roles) unless the change states them. Never answer for the author. Required before drafting: scope, addon, characters, output path, locale, depth, clients, log source, settings.

1. **Scope.** "What is in scope: the current branch, a diff (which range), or this session?" Read it. In a second turn, show the list of what changed and what could break and ask the author to correct it. If an OpenSpec change exists, use its proposal, specs and tasks as the checklist.
2. **Addon.** Which addon does the plan test (its folder name), and which slash prefixes does it use? For an addon CheckThat does not know ("Supported addons" in `reference.md`), list its prefixes in the plan's `commands` and suggest the addon declare them with `CheckThat.Commands`.
3. **Characters.** "Does any check need data or actions from more than one character?" Most scopes need one. A run belongs to the character that started it, so a check that needs several characters becomes one plan for each character role, and a comparison afterward (section 2). Ask which roles exist and what each one holds or does. Name each role in one short word. There is no limit on the number of roles; two is the usual case.
4. **Output.** "Where should I write the plan?" Suggest `plans/` in the repository you are working in. Accept any path. Ask for the file name. Suggest `<addon>.yaml` for one plan, `<name>.<area>.yaml` for each plan of a set by area, and `<name>.<role>.yaml` for each plan of a role set (for example `keepthat-tally.bank.yaml`). Add the locale for non-English plans (for example `<addon>.deDE.yaml`).
5. **Locale.** Which client locale will the plan run on? Write the plan for that locale only. Authors keep one plan per locale. Do not translate. Player-visible text in the plan uses the strings that locale shows.
6. **Purpose and depth.** Ask first what the plan is for, and set `purpose` on the plan to the answer:
   - **Foundation** (the release gate): "Do the systems that everything else depends on work in the real game?" Interview for the pillars before any step: which systems, if they fail, make every feature fail? Name each pillar with its real-game risk only, the thing a unit test or the offline block cannot catch: a game call that is missing or shaped differently on one client, a real event that never reaches the decision, shipped data or the player's position that is wrong, a call that succeeds but draws nothing, a window that gives no id or position, saved data lost on `/reload`, a Lua error on either TOC. Confirm the pillars with the author. Ask which surface they find critical. Draft it as in "Foundation plans" (section 2).
   - **Feature** (go deep): "Does this feature work in every case the real game can produce?" Interview for the cases: edge and negative cases, each client, the roles it needs (item 3), and combat or instances when the feature touches them. It runs when the feature is developed or changed, not before every release. Ask whether it is retired or kept as a regression plan after the feature ships. When it needs a staged character (a class, a profession, a place), the preamble says so.

   Then ask: what is the riskiest part of the scope? What must never break? Scope before you draft or convert anything, also a manual test document (`ct.py from-md`):
   - A plan checks only what a fake game cannot prove: real game data and events, end-to-end wiring, drawing, sound, other addons, and saved variables across `/reload`. Logic that a unit test proves gets no plan step. For each candidate check, ask whether a unit test already proves it, and show the author the list.
   - Measure, do not guess. Run the addon's unit tests with coverage when it has them, and map the scope's spec requirements to plan steps (`ct.py coverage`, section 4) and to unit tests (`-- covers: <Requirement name>` comments, read by the same command). Base the purpose and depth answer on that map.
   - Offer an essential draft first, never a one-for-one conversion of a manual document. Each step covers a whole feature from start to finish, not one facet.
   - A foundation plan has about one step per pillar, 8 to 12 steps. Any plan has at most 25 steps and a section at most 10. A larger feature scope becomes a plan set by area (section 2).
7. **Clients.** Which clients are in scope: `classic-era`, `forever-camelot`, or both? Which steps are for one client only?
8. **Evidence.** Align with the addon's own logging; do not require a CheckThat-style log. Ask these one at a time:
   - What is the debug-log SavedVariable name, its path inside it, and its format (`strings` or `entries`)? Check the addon source first (and "Log sources" in `reference.md`), then confirm with the author.
   - Which behaviors already write a log line? Read the addon source for the lines. Do not invent lines.
   - Which scope items write nothing? Those need a player check (see item 9). A result that is a value, or has no log line, can also become a fact: the addon calls `CheckThat.Report` and the plan asserts on a `facts` log source (see "Publish a fact" in `$CT/docs/debug-logging.md`). Offer it beside a new log line, and never write an assertion for a fact the addon does not report.
   - If the addon has no debug log at all, say so once and recommend adding one. Point to `$CT/docs/debug-logging.md` for the pattern and what a good line looks like. Ask: add one now, or draft with player checks? Either way, draft player checks, never invent log lines, and mark each step that would become a log assertion once the log exists (`notes: Becomes a log assertion once <addon> logs <event>.`).
9. **Human eye.** For each changed behavior with no log line: can the author accept a player check, or should the addon gain a log line or report a fact? List suggestions and let the author accept them all or decide one by one. What needs combat, a protected action, or a second client? Also ask which scope items need no client at all (classification, counts, settings state, export contents). A plan's `offline:` block calls the addon's `CheckThat.Entry` functions in the fake client (`ct.py offline`) and is cheaper than a player step. Give a new block `level: 6`, and mock only functions the TOC's client has. Prefer a recorded answer to a guessed one: a mock entry `{ recording: "GetItemInfo(6948)" }` replays what the game returned for that call (the labels are in `$CT/tools/recordings/<client>.json`; `ct.py recordings` makes them from a CTProbe run). At level 6 a game global that addon code replaces reads as insecure to `issecurevariable` for good, and a mock of a game function does the same, as in the game. When the addon ships a TOC for each client, add `tocs: { era: ..., forever: ... }` and run `ct.py offline --client both`, so a call that only one client lacks fails in that client's cases. A `tooltip` step (level 5) checks the lines an addon put on `GameTooltip`: `lines` as a count, or `equals` or `contains` text for any line or one `line`. Use `groups` when cases need opposite mocks or a clean start, a `reload` step when state must survive `/reload`, and a `wait` step when something happens after a timer. Give an `event` step every value the event always carries. Draft those first, then ask for player steps only for what the log cannot show. See "Offline" in `$CT/docs/authoring-plans.md`.
10. **Reload and state.** Which steps need `/reload`? Which checks survive a reload and which are per attempt or per session? What setup and cleanup does each step need?
11. **Settings.** "Does any step depend on the addon's own settings?" A plan written for the default settings fails for a tester who changed them, and a command that sets a value overwrites the tester's own setting. If it does, recommend a test-settings mode in the addon: one command puts the character's settings aside and uses fresh defaults, a second restores them exactly, and the mode lasts across `/reload`. Then the plan's setup step runs debug on, the test-settings command and `/reload`, in that order, and its last step turns the mode off and asserts the restore line. Debug goes on first, because the addon drops lines while its log is off. Never recommend per-step setting commands that overwrite the tester's settings. The mode is addon code: offer an issue (section 5) if the addon has none. See "Test settings" in `$CT/docs/authoring-plans.md`.
12. **Return path.** Remind the author the result comes back by `/ct export`, then `/reload`, then `ct.py collect`, and then the `verify` skill reads it back. The tool needs the WoW SavedVariables path; ask for it only if the author wants to harvest now. The tool reads `CT_WOW` (the game folder) from `$CT_ENV`, `.ct.env` or `~/.checkthat.env`, so ask for the path once and offer to write it there.

## 2. Draft

Draft **one plan at a time and one step at a time** (section 4 reviews each step as you draft it). Write YAML to the chosen path. Follow `example.yaml` for shape and the schema for fields. The rules that decide the draft:

- **Simple steps by default.** Each step has one player action and one expected result, in short active sentences. When a check needs more, split it into consecutive steps. Draft a compound step (several actions, several expected results or a multi-part assertion set) only when the author asks for it, say that you did, and mark it with `notes: Compound step, drafted on request.`.
- **Actions as a list.** When one result needs two to six player actions in a row (walk in, wait, walk out), write `action.text` as a list, one action per item. The card shows a checkbox for each, which the player ticks. Write several results as a list in `expect` the same way. Keep one action or one result as a string. A `copy-slash` step's text stays one command.
- **Checked at run start.** A check that needs no player action and no time window (a startup line, a `version` fact the addon reports at login, a state probe) can be an `auto` step with `async: true`. CheckThat judges it when the run starts, against the whole retained log (also earlier sessions), so use a check only this build can meet, such as a `version` fact with `eq`. The card never stops there. It cannot have `setup`, a `call`, a reload or an absence check.
- **Steps for one character.** In a feature plan, a step that needs a class or a profession gets a requirement with `class` (tokens such as `MAGE`) or `profession` and `unmet: inapplicable`. On another character the step does not apply and does not fail at its timeout.
- **Start with a version check.** The first step of every plan checks that the game loaded the version under test. A copy of an older build gives results that mean nothing. Use an `auto` step when the addon reports a `version` fact; otherwise ask the player to read the version in the AddOns list. The recipes are in "Version check" in `reference.md`.
- Cover each changed requirement or scenario that a fake game cannot prove with at least one step. Add one regression step for the nearest unchanged behavior. Add negative cases, and combat cases when the scope touches them. Keep a foundation plan to about one step per pillar, and any plan to at most 25 steps and each section to at most 10.
- Prefer a required `log` assertion where the addon already logs the evidence. Use `diagnostic` only for extra context. Use `absent` for "must not appear". Pick `scope` on purpose: use `attempt` for evidence expected after the step opens (attempts survive `/reload`); use `session` only for a line an earlier step wrote. Prefer `contains` or `equals` to a `pattern`. A pattern (and a `matches` value) is a Lua pattern of up to 200 characters. `validate` refuses one that Lua cannot read (an open `(` or `[`, a lone `%`). A line that takes too long to match leaves the step unverified ("a log line took too long to check with this pattern"); see `$CT/docs/authoring-plans.md`.
- Where nothing is logged, use `verify: [player]` and an `expect` a player understands. Never ask the player to read a log line. A disabled button or a refusal that writes no line is a player check and a gap for section 5. Do not stand in with an unrelated `absent` line.
- A confirmation question that the action itself raises is part of that action, not a second action.
- Put a destructive step (delete, clear, reset) last, and say in its `setup` to export the run first, because it removes evidence.
- Group steps into `categories` (or let each section be one) when the plan has areas a tester may run on their own. Use a `fact` assertion for a value (`between`, `approx`, `type`, `in`), `count` for "how many times" (`min` on an auto step), and the quiet `errors` source (`global.errors`) for "no Lua error". Use `cases` for one check repeated over a list. Read "Unit-test checks" in `$CT/docs/authoring-plans.md`.
- Mark a step `auto: true` only when its required assertions are unconditional log lines or state probes that settle the step alone, with `verify: [assertions]` and no `player`. A required check that something did not happen (`absent`, a `missing` fact, a count with `exactly` or `max`) is allowed only with a `timeout`: the step passes when the time ends with the check still holding, and fails at once if it breaks. CheckThat then records the result itself. A step that needs a human judgment ("it looks right") stays manual. Default an auto step's `timeout` to 120 seconds, and ask the author whether to change it (5 to 300 seconds). Tell them the timeout counts from when the step opens, so it must cover the player's own action time plus the result. At the timeout a contradicted check records fail and missing evidence records unverified, never fail. Use `kind: wait-event` for a step the player finishes by doing something in game. It is valid only on an auto step.
- Ask the author for each step: auto or manual. A manual step waits for a click, so end its `expect` text with the press it needs (for example "Press Pass."). Never leave a tester waiting for a step that will not advance by itself.
- Never assert the line a step's own result press writes (`[ct] step <its id> <verdict>`). CheckThat judges the result before it writes that line, so the step stays unverified. Put such a check on a later step with `scope: run`.
- A check for new UI says what the tester should see: where it appears, which way it grows, what it shows. "It shows" is not enough.
- Every slash command named in step text goes in that step's `action.commands`, and only from the addon's allow list (or the plan's `commands`) plus `/reload`, `/reloadui` and `/console scriptErrors 0|1`. No `/script`, `/run` or `/dump`. The card shows four command lines, so keep a step to four.
- **Name earlier steps by what the player did.** The card shows step titles, not ids, so "the vendor you opened in check 1.3" cannot be followed. Write "the vendor you walked to after the first sell question". `validate` warns about a step number or one of the plan's ids in action text, `setup` or Expect; `notes` and `reviewer` may name ids.
- **Player language.** Action text is one sentence about what the player does. Commands sit only in `action.commands`, behind Run: write "Press Run to show a test question.", not the command itself. Expect states what is on screen, never what is logged. Flag any step whose action text or Expect shows a slash command, or whose Expect speaks of the log; `validate` warns about both when the plan sets `purpose`.
- Text uses native color codes (for example `|cffffd100Pass|r` for a button name), never Markdown. Sentences are short, active voice, one fact each.
- Tag steps with `clients` only when they apply to one client; a step for both clients has no tag. Add `setup`, `cleanup` and `reload` where the step needs them.
- Never put raw saved variables or real character names in the plan.

### Foundation plans

A foundation plan (`purpose: foundation`) is the release gate: a tester runs it on each client before each release.

- **One character.** Any class, any level, no profession, in one stated place (for example a capital). One run per client. The preamble lists these assumptions.
- **What leaves the gate.** A step that needs a class, a profession, a place, a dungeon, a fight or another addon is not foundation. Move it to a feature plan, the offline block (a recorded call) or a unit test. The preamble names each one and where it went, so the author accepts the gap knowingly.
- **One step per pillar.** One section per pillar, titled with the pillar's name, with one step (at most about two). Prefer automatic steps. Keep a player step only for what is drawn or heard, and for the surface the author named as critical.
- **Settings are mocked, the game is not.** Use the addon's test-settings mode (interview item 11) and push real thresholds to their limits. At least one step crosses a real threshold end to end, because a "test now" command skips the wiring. Mocks stay in the offline block.
- **No restore steps.** No step exists only to put one setting back: the step that turns test settings off (interview item 11) restores them all.
- The plan keeps its version step first. It ends with the test-settings off step, when the plan uses the mode, and a no-Lua-error step (the quiet `errors` source with `scope: run`).

### Plan sets by area

When the essential steps of a feature plan are still more than 25, split the scope into a set of plans by area (for example core, interface, other addons). The same character runs them one after another. A set by area is not the release gate: the foundation plan is.

- Each plan has its own version step, its own setup step and a final no-Lua-error step (the quiet `errors` source, see "Unit-test checks" in `$CT/docs/authoring-plans.md`). Give that step `scope: run`, so it sees every error since the run started and none from an earlier run or plan.
- Section ids and step ids do not overlap between the plans of a set: give each plan its own section range.
- File names are `<name>.<area>.yaml`. Each preamble names every partner plan file and says to run all of them when the feature changes. Say "before each release" only when the author asks for it.
- Starting a run uses the last plan imported for that addon. Tell the author to import, start and finish each plan before importing the next.

### One plan for each character role

When the interview named more than one role, draft one plan for each role. See `keepthat-tally.bank.yaml` and `keepthat-tally.alt.yaml` beside this file.

- Each plan is runnable by its character alone. No step asks the player to log in as another character.
- File names are `<name>.<role>.yaml`. Each preamble names every partner plan file and says to run all of them before verifying.
- A `reviewer` line on the step that completes a comparison (usually in the last role's plan; the other plans need none) names the partner files, the step IDs to compare and the relationship that must hold (for example "both tooltips show the same total"). The `verify` skill reads it. Reference a step as a file name plus a step ID, because step IDs are local to a plan.
- Step IDs stay stable and carry a per-role prefix.
- Compare nothing in game. The comparison happens afterward from the collected results.
- Starting a run uses the last plan imported for that addon. Tell the author to import and start each role's plan on its own character before importing the next.

## 3. Validate

Run `$PY $CT/tools/ct.py validate <plan> --addon-src <addon folder>` on every plan (leave out `--addon-src` when the source is not at hand). Report every problem with its step id and fix it. `validate` fails on a step that asserts its own result line. It warns (without failing) about a slash command named in text but missing from `commands`, about a first step with no version check, and about a plan over 25 steps or a section over 10 (each case counts as a step). When the plan sets `purpose`, it also warns about a slash command in action text or Expect, about the log in Expect, and about a foundation plan over 12 steps. It warns about a step number in player text, and, with `--addon-src` or the plan's `offline.toc`, about a version step that accepts an older build than the addon's TOC. Fix each warning.

## 4. Review

Review while you draft: show each step with its evidence choice and client tags and its findings from `reference.md`, and apply only what the author accepts before you draft the next step. A rejected new step stays out of the plan. A rejected edit to an accepted step leaves that step as it was. If the author asks for an edit without wording, ask for the wording before you show it. Offer "accept all" only when the author asks for it.

After the last step, run the handoff gate. Do every part, in this order, and fix each finding in the same session; do not file findings as issues and stop.
1. `$PY $CT/tools/ct.py validate <plan> --addon-src <addon folder>`, then `compile <plan> -o <file>.ct`.
2. `$PY $CT/tools/ct.py replay-flow <plan> [--hooks <file>.lua]`. It plays every step in the fake client (the bundle has it; it needs `luajit`) and exits 1 on a problem: a step that never settles, a card that shows a step twice, a step never reached. Lines and facts from the addon's own log are written by the replay, so it prints "evidence assumed": it proves the plan flow, never that the addon writes the lines. Without `luajit`, say that the plan was not replayed.
3. `$PY $CT/tools/ct.py lines <plan> --addon-src <addon folder>` checks that each asserted log line and fact key appears in the addon's Lua source. A miss is a warning to check by hand (a line built at run time matches on any run of its words of at least 8 characters, for `equals`, `contains` and `pattern` alike; a value placeholder in a `pattern` is then not checked).
4. If the plan has an `offline:` block, `$PY $CT/tools/ct.py offline <plan> --addons <folder above the addon>`.
5. An independent review of the final plan against what the card shows: the Run button, the copy boxes and the chat sentences (`$CT/CheckThat/UI/Card.lua`). Use a second model or a fresh reviewer when you can. A step whose own commands move the card (`/ct pass`, `/ct next`, ...) gets a `validate` warning: take the command out or say "on purpose" in the step's notes.
6. Tell the author which plan version any earlier in-game run used, and what changed since. Never claim a later edit was tested by an earlier run.

Then show the author:
- For a foundation plan: every step the stated character cannot do (it needs a class, a profession, a place, a fight or another addon), every pillar with no step, and every pillar with more than about two steps. Move each such step out and name it in the preamble.
- Coverage: each scope item and the step(s) that cover it; gaps in bold. When `$CT` and the addon source are at hand, `$PY $CT/tools/ct.py coverage <plan...> --addon-src <addon folder>` lists the subcommands, settings and spec requirements no step touches, and which requirements unit tests already cover (a plan step on those may repeat a test); a step or section names a requirement with `covers: [heading text]`.
- For a set of plans: each preamble names every partner file, and the reviewer line names the partner files and step IDs.
- The checklist in `reference.md`, with each finding tied to a step id.

Re-run `validate` and the gate after changes, then run `compile <plan> -o <file>.ct` on every final plan. Check the text of every step the replay warns about (see "Replay a plan" in `$CT/docs/authoring-plans.md`). For a set, tell the author the import order: for a role set, one role per character, each imported and started before the next import; for a set by area, each plan imported, started and finished before the next import.

## 4b. Step ids stay put

A step id is a key: `ct.py diff` and `trend` follow a step by its id. When you edit an existing plan, never renumber or rename an id. Add a new step with a new id (append to the section, or use the next free number), and retire a step by removing it. `ct.py diff` reports a step that kept its text but changed its id as "renamed" and warns that its history is split.

## 4c. Revise after a run

Use this when the author has run a plan and wants it fixed. Never edit addon code unasked.

1. Collect and read the run with the `verify` skill's commands first: `$PY $CT/tools/ct.py report --failed-only --dest <evidence> --addon-src <addon folder> --plan <plan file>` (the expected version comes from the addon's TOC; give `--expect-version <addon version>` when the source is not at hand). Relay every `warning:` before anything else. A run of another build, or of an older plan file, says nothing about the current plan: stop and ask for a new run.
2. Sort each failed, unverified or contradicted step with `ct.py show <run> <step>` (attempts, `rule`, `hits`, `excerpt`, error stacks):
   - **Plan fault.** The step asserts its own result line; the log was not readable (debug not on, wrong log source or path); the pattern is stricter than the line the addon writes (a hit shows a near match); `scope` is wrong; the timeout is too short; the step order or the `expect` text sends the tester the wrong way; a manual step's Run button moved the card.
   - **Addon fault.** The rule is right and the evidence contradicts it: a forbidden line appeared, a state check failed, a Lua error from the addon fell inside the step.
   - **Cannot tell.** Say so and ask the author. Do not guess.
3. Edit only plan faults, keep every step id (section 4b), and run the handoff gate (section 4) again. Then replay the revised plan against the failing run: `$PY $CT/tools/ct.py replay <plan> --run <run id> --dest <evidence>`. It judges every log and fact check against the log the game really wrote, so a wrong line order or a reworded line fails here, which `replay-flow` cannot show. Fix each failure before you ask for another in-game run. A pass proves only the checks that read the whole log: a check that needs the step's own window (`absent`, `exactly`, `max`, a `missing` fact) and a state probe are "not judged offline". Say which plan version the run used and which plan version you now hand over.
4. Tell the author what to do next:
   - Addon faults only, plan unchanged: fix the addon, `/reload`, then `/ct rerun failed` in the same run.
   - The plan changed: import the new plan and start a new run (the old run belongs to the old plan digest). `/ct run <category>` limits it to the areas that failed.
   - After the new run, `$PY $CT/tools/ct.py diff <old run> <new run> --dest <evidence>` shows which steps were fixed, regressed or are not comparable. A `not-comparable` step is unknown, not fixed.
5. Report three lists: plan faults fixed (step id, what changed), addon faults for the author's code (step id, the evidence that shows it), unknown steps.

## 5. Gaps

For every step that has no log evidence, offer to open an issue in the addon's repository: `gh issue create`, with the gap, the code involved and a possible log line or fact (the guarded `CheckThat.Report` call and its key, from `$CT/docs/debug-logging.md`). If the addon has no debug log, offer one issue for the log facility (the pattern in `$CT/docs/debug-logging.md`) plus one issue per needed line, each naming the steps it unlocks. No personal names. Ask first; never open it unasked.
