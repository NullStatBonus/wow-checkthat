# Design

## Context

Lua pattern matching backtracks, and the cost depends on the pattern and the line together. Measured in LuaJIT on lines of one repeated character: `.-.-.-Z` takes 0.37 s on 200 characters, `.-.-.-.-Z` 15 s, `%d?` repeated 20 times then " ms" on 51 digits 274 ms, `a?` repeated 26 times then `b` on 60 `a` 26 s. `pcall` does not bound time and the addon cannot use `debug.sethook`. Rules about the shape of a pattern cannot bound it: a count of repeats or a ban on repeats side by side refuses ordinary linear patterns that plans used before (`%d+%.?%d*`, `(%S+)%s+(.+)`, `.*%d+`, `%[(.-)%]%s*(.*)`), and still lets slow ones through (optional items, repeats separated by a literal). Cutting the line changes verdicts (a forbidden line past character 1000 would pass). The only bound that does not change a verdict is to run the match ourselves and stop it.

## Goals / Non-Goals

**Goals:** a plan can never freeze the client with a pattern, whether it was compiled with the new tools, imported from an old string or stored in saved variables; no plan that worked keeps from working; the validators agree with the addon; `compile` and the schema match what the game imports.

**Non-Goals:** changing the plan format version; matching captures (a plan only asks whether a line matches).

## Decisions

- **A hybrid: plain search, `string.find`, and a matcher with a step budget.** The C matcher is about 100 times faster than a matcher written in Lua, and for a pattern with one unbounded repeat its cost is bounded by the line and the pattern, so it stays for the common case. (1) A pattern with no special character (`^$*+?.([%-`) is a plain search, as in `string.find`. (2) A pattern with at most one `*`, `+` or `-`, at most three `?` and no back reference runs `string.find` on a line of at most 2000 characters, when the estimated work is at most 4,000,000 units. The work is the start positions (one when the pattern is anchored; the count of the first literal character when the pattern starts with one; else the line length) times the reach of the repeat (the line length, or 1 with no repeat) times the items plus one, doubled for each `?`. A leading `.*` or `.-` (also inside plain `(`) is not counted and is dropped by running `^` plus the pattern: a match from a later start is also a match from the first, as the leading repeat takes the text before it. It does not hold with a back reference, so that is excluded; the differential test checks it on more than 10000 cases with captures. (3) Everything else, and a simple pattern on a longer line, runs `Pattern.Match`, a port of `str_find_aux` and `do_match` of Lua 5.1 `lstrlib.c` (single characters, classes, sets, `.`, anchors, `* + - ?`, captures, back references, `%b`, `%f`) that counts steps: an item call, a character test, a set item read, a `%b` scan character. When the steps pass `Pattern.BUDGET`, the match is abandoned and the line is "could not be checked". No game globals, Lua 5.1 syntax.
- **Measurements** (LuaJIT with the JIT off, the nearest to the game's Lua here; PUC Lua is not installed). A port step costs 66 to 164 ns. `Pattern.BUDGET = 40000` steps is 2 to 7 ms for one line: two sets of 70 items followed by `x` on 300 `a` 2.4 ms, `.-.-.-.-Z` on 1000 `a` 3.1 ms, `%d?` 20 times then " ms" 4.4 ms, `%w+%s*=%s*%d+` on 300 `a` 7.1 ms. Native `string.find` costs 0.4 to 1.1 ns a work unit: `a.-b` on 2000 `a` is 10 ms (work 1.6e7, so it goes to the port), `a?a?a?a.-Z` on 1000 `a` is 21 ms (work 5.6e7, port), `.-` before a 190-character tail on 1000 `a` is 220 ms natively but is a stripped pattern and costs 0.7 ms. So 4,000,000 units is at most about 4.5 ms. Ordinary text of 150 to 2000 characters is never left unchecked for `.*failed`, `.-failed`, `.*error.*`, `(.*)failed`, `.*%d+`, `%w+%s*=%s*%d+`, `%d+%.?%d*`, `(%S+)%s+(.+)`, `%[(.-)%]%s*(.*)`, `^%s*(.-)%s*$` and every pattern in `plans/`; a long token with no space (`(%S+)%s+(.+)` on 150 `a`) is quadratic and is left unchecked.
- **A pass allowance, for the live card only.** One refresh (`Evidence.Preview`) may spend `Pattern.PASS_ALLOWANCE` = 150000 steps on lines whose answer is not kept: about 11 to 18 ms. A native call is charged work / 100 plus 4 plus a sixteenth of the line length; about 1 microsecond for a short line. When it is spent, a line not seen before is pending: not run, not kept, the check is unverified with "still checking the log (the card tries again)". Anything that records a result (`Run.Verdict`, an automatic pass, a timeout) calls `Evidence.Check`, which runs with no allowance (`Pattern.Unmetered`), as a result is written once and never retried; the budget for one line still applies, so judging 300 over-budget lines can take about a second once. The next refresh goes on from the kept answers, so a long log settles in a few refreshes, and one over-budget line costs 2 to 7 ms instead of 300 of them costing seconds.
- **Cache.** `Pattern.Find` keeps the answer for each pattern and line, "could not be checked" too, in two generations of up to 20000 pairs. A hit in the older generation moves to the newer one. At the start of an evaluation, a newer generation that holds 20000 pairs becomes the older one and the older one is dropped, so one evaluation never loses what it just kept, and a window above 4000 lines is reused by the next refresh. Pending lines are not kept.
- **Verdicts for a line that could not be checked.** The line is neither a match nor a miss. A positive match on another line still passes. An absence, a count with a maximum or an exact value, a positive match with no other matching line, a sequence, and a `matches` fact or state are unverified with "a log line took too long to check with this pattern" (or "still checking the log" when a pass ran out of allowance: that reason wins, as a later pass can settle it). More real matches than a count allows still fail. For a fact, `which: any` passes when one value matched and `which: all` fails when one value broke the operator, whatever another value did.
- **Validation keeps only what `string.find` raises on.** `Plan.PatternProblem` refuses a non-text pattern, one over 200 characters, and one with an unclosed set, a lone trailing `%`, unbalanced captures, a back reference to a capture that is not closed, `%b` without two characters, `%f` without a set, or more than 32 captures. A pattern with no special character is accepted, as `string.find` treats it as plain text. A pattern with a NUL byte is refused ("pattern has a NUL byte; write %z"): Lua 5.1 ends a pattern at a NUL, so `string.find` and a port that reads the whole string would disagree. `tools/ct.py` `pattern_problem` mirrors it (bytes, same reason text). `tests/fixtures/parity-patterns.json` and a generated set of 4000 patterns, run through `luajit`, keep them equal. The Lua side also probes the pattern once with `string.find` on one character.
- **The guard sits in `Evidence`, not only in import.** A plan already stored, or imported by an older version, is not re-validated. `Evidence.Check*` returns `unverified` with "pattern ...; it was not run" before it reads a log, so an absence or a count of at most n cannot pass. A pattern the validator missed that raises in the matcher is treated as unchecked.
- **Types are checked where the plan is read.** `Plan.Validate` gains `textField`, `listField` and `checkMatcher` for the sites that crashed: log sources, requirements, preamble, handoff, section intro and setup, step setup, assertion label, matcher fields, sequence items. Optional fields stay optional. `Evidence.ReadLog` also returns nil for a source that is not a table, for plans stored earlier.
- **`null` in `ct.py`.** `validate` walks the plan (not the tools-only `offline` block) before the schema and names each path. The schema gives `value` a type list that excludes null.
- **Import cap.** `MAX_ENCODED = 120000` sits next to `MAX_INFLATED` in `tools/ct.py`, with a test that reads `Codec.lua`.
- **`tools/replay_sv.lua`** loads `Plan.lua` and `Pattern.lua`, since `Evidence` uses both.

## Compatibility

This is a fix. The only pattern that is newly refused is one that `string.find` raises on, so no plan that worked is refused: a check on it raised an error. Every other pattern is accepted and matched on the whole line as before. A line that takes too long used to freeze the game; it is now unverified. A plan with `pattern: "%1"` (a back reference to no capture) was accepted and could never match; it is now refused as invalid. Fields that the game could not read (`null`, wrong types, empty required text) were already refused or crashed the card; the validators say so up front. Optional fields and unknown keys are unchanged. No format revision and no offline level are needed: a check that fails only code the game itself rejects is a fix.

## Risks / Trade-offs

- The port runs in Lua, about 100 times slower than the C matcher: it is used only for patterns with several repeats or back references, and for a simple pattern on a line over 2000 characters or with a high estimated work. A line is checked once and then kept.
- A quadratic pattern with several repeats on a long line (`(%S+)%s+(.+)` on 150 or more characters with no space) passes the budget and leaves the check unverified where `string.find` would have said "no match". The reviewer reads the reason. An author uses `contains`, or anchors the pattern.
- The budget is measured on LuaJIT without its JIT. The game's Lua may be slower per step; the bound is then somewhat above 5 ms for the same line, never unbounded.
